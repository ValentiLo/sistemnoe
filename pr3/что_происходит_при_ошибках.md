# Что происходит при ошибках с памятью

Разберём три классические ошибки: **двойной `free`**, **use-after-free**, **утечка**. Для каждой — причина, что происходит в памяти, чем опасно, как найти и как избежать.

---

## 1. Двойной `free` (double free)

### Что это

Программа вызывает `free` для одного и того же указателя **дважды**.

### Код с ошибкой

```c
int *p = malloc(10 * sizeof(int));
// ... работа ...
free(p);     // первый раз — OK
free(p);     // ❌ второй раз — ОШИБКА
```

### Что происходит в памяти

**После первого `free(p)`:**

```
Программа (стек)              Куча (heap)
┌──────────────┐             ┌────────────────────────────┐
│ p = 0x1000   │ ─────────→  │ (свободно)                 │  ← блок вернулся
└──────────────┘             │  0x1000                    │
                             └────────────────────────────┘
```

Указатель `p` **всё ещё хранит адрес** `0x1000`, но эта память уже **не принадлежит программе**.

**После второго `free(p)`:**

Куча пытается освободить блок, который **уже свободен**. Что произойдёт — **непредсказуемо**:

- Куча может **испортиться** (повреждение внутренних структур).
- Программа **упадёт** с `Segmentation fault` или `Aborted`.
- Иногда **«повезёт»** — ничего не произойдёт, но ошибка «спрячется» и проявится позже.

**Диалог:**

> *Программа:* — Куча, освободи блок `0x1000`.
> *Куча:* — Стоп! Этот блок уже свободен. Ты меня обманываешь! Аварийное завершение.

### Чем опасно

- **Повреждение кучи** — другие `malloc`/`free` начнут работать неправильно.
- **Уязвимость безопасности** — злоумышленник может использовать двойной `free` для **внедрения своего кода** (классическая атака через heap exploitation).
- **Трудно найти** — ошибка может проявиться через много секунд после фактического `free`.

### Как избежать

**Всегда обнулять указатель после `free`:**

```c
free(p);
p = NULL;   // защита
```

Тогда второй `free(p)` вызовет `free(NULL)` — **безопасно**, ничего не делает.

### Как найти

**Valgrind:**

```bash
valgrind --leak-check=full ./app
```

Вывод:

```
Invalid free() / delete / delete[] / realloc()
   at 0x...: free
   by 0x...: main (main.c:15)
 Address 0x... is 0 bytes inside a block of size 40 free'd
```

**AddressSanitizer:**

```bash
gcc -fsanitize=address -g -o app main.c
./app
```

Вывод:

```
ERROR: AddressSanitizer: attempting double-free on 0x...
```

## 2. Use-after-free (использование после освобождения)

### Что это

Программа **обращается к памяти** после того, как она была **освобождена**.

### Код с ошибкой

```c
int *p = malloc(10 * sizeof(int));
p[0] = 42;
free(p);

printf("%d\n", p[0]);   // ❌ используем после free
p[1] = 100;              // ❌ пишем в освобождённую память
```

### Что происходит в памяти

**После `free(p)`:**

```
Программа (стек)              Куча (heap)
┌──────────────┐             ┌────────────────────────────┐
│ p = 0x1000   │ ─────────→  │ (свободно)                 │
└──────────────┘             │  0x1000                    │
                             └────────────────────────────┘
```

Блок помечен как свободный, но **память не стёрта**. Там всё ещё лежит `42`.

**Что происходит при `p[0]`:**

1. Программа читает по адресу `0x1000`.
2. Значение там пока `42` — **но это случайность**.
3. Если между `free` и чтением **другой `malloc`** забрал этот блок — там уже **другие данные**.
4. Если блок отдан системе — **Segmentation fault**.

**Схема с переиспользованием:**

```
После free(p):                 После q = malloc(10):
┌──────────────────┐          ┌──────────────────┐
│ [ 42 ][ ... ]    │   →      │ [ 99 ][ ... ]    │  ← q занял тот же блок
│  0x1000 (свобод) │          │  0x1000 (занято) │
└──────────────────┘          └──────────────────┘

p[0] всё ещё читает 0x1000 → получает 99 (не 42!)
```

**Диалог:**

> *Программа:* — Читаю `p[0]`.
> *Куча:* — Ты уверен? Этот блок я уже отдала другому. Там сейчас `99`.

### Чем опасно

- **Непредсказуемые данные** — программа работает «неправильно», но не падает.
- **Повреждение чужих данных** — если писать по «освобождённому» адресу, можно испортить данные другой программы.
- **Уязвимость безопасности** — классический сценарий для эксплойтов.
- **Трудно отлаживать** — ошибка плавающая, зависит от порядка `malloc`.

### Как избежать

**Всегда обнулять указатель после `free`:**

```c
free(p);
p = NULL;
```

Тогда `p[0]` сразу вызовет **ошибку** (`Segmentation fault`), а не вернёт мусор. Это лучше — ошибка проявляется **сразу**, а не через час.

**Не хранить копии указателей:**

```c
int *p = malloc(...);
int *q = p;      // две ссылки на один блок
free(p);
q[0] = 5;        // ❌ use-after-free через q
```

### Как найти

**AddressSanitizer** — лучший инструмент:

```bash
gcc -fsanitize=address -g -o app main.c
./app
```

Вывод:

```
ERROR: AddressSanitizer: heap-use-after-free on address 0x...
READ of size 4 at 0x... thread T0
    #0 0x... in main (main.c:8)
```

**Valgrind:**

```bash
valgrind ./app
```

Вывод:

```
Invalid read of size 4
   at 0x...: main (main.c:8)
 Address 0x... is 0 bytes inside a block of size 40 free'd
```

## 3. Утечка памяти (memory leak)

### Что это

Программа **выделяет память**, но **не освобождает** её. Блок остаётся занятым до завершения программы.

### Код с ошибкой

```c
void process(void)
{
    int *p = malloc(1000 * sizeof(int));
    // ... работа ...
    // забыли free
}

int main(void)
{
    for (int i = 0; i < 1000000; i++) {
        process();   // ❌ каждый вызов теряет 4000 байт
    }
    return 0;
}
```

### Что происходит в памяти

**После первого вызова `process`:**

```
Программа (стек)              Куча (heap)
┌──────────────┐             ┌────────────────────────────┐
│ p = ?        │             │ [ 4000 байт занято ]       │  ← блок осиротел
└──────────────┘             │  0x1000                    │     (нет указателя)
                             └────────────────────────────┘
```

**После миллиона вызовов:**

```
Куча (heap)
┌─────────────────────────────────────────────────────────┐
│ 4 ГБ занято — вся память съедена                        │
│ ... 1 000 000 блоков по 4000 байт ...                   │
└─────────────────────────────────────────────────────────┘

Следующий malloc → NULL → программа падает
```

**Диалог:**

> *Программа:* — Куча, дай ещё 4000 байт.
> *Куча:* — Извини, я вся занята. Ты **никогда** не возвращал мне блоки. Больше нечего дать.

### Чем опасно

- **Программа «съедает» память** — свободная память заканчивается.
- **Система начинает тормозить** — уходит в своп.
- **Программа падает** — `malloc` возвращает `NULL`, а программа не проверяет → краш.
- **Долгоживущие процессы** (серверы, демоны) — **особенно** опасны, утечка накапливается месяцами.

### Разновидности

| Тип утечки | Что происходит |
|------------|----------------|
| **«Забыли free»** | Указатель потерян, блок занят |
| **«Потеряли указатель»** | `p = malloc(...); p = malloc(...);` — первый блок недоступен |
| **Утечка в цикле** | `malloc` без `free` на каждой итерации |

### Как избежать

1. **Парность:** каждый `malloc` → `free`.
2. **Проверка:** после `free` → `p = NULL`.
3. **Умные указатели** — в C++ (`unique_ptr`, `shared_ptr`), в C их нет.
4. **Отслеживание** — оберните `malloc`/`free` в свои функции со счётчиками (для отладки).
5. **Инструменты** — `valgrind` и санитайзеры покажут, **где** утечка.

### Как найти

**Valgrind:**

```bash
valgrind --leak-check=full ./app
```

Вывод:

```
HEAP SUMMARY:
    in use at exit: 4,000,000 bytes in 1,000 blocks
  total heap usage: 1,000 allocs, 0 frees, 4,000,000 bytes allocated

LEAK SUMMARY:
   definitely lost: 4,000,000 bytes in 1,000 blocks
   ...
    at 0x...: malloc
    by 0x...: process (main.c:5)
    by 0x...: main (main.c:12)
```

**AddressSanitizer** покажет **меньше** — ему сложнее ловить утечки, но тоже умеет:

```bash
gcc -fsanitize=address -g -o app main.c
ASAN_OPTIONS=detect_leaks=1 ./app
```

## Сравнительная таблица

| Ошибка | Что делает программа | Что происходит | Как проявляется |
|--------|---------------------|----------------|-----------------|
| **Двойной `free`** | `free(p); free(p);` | Повреждение кучи | Краш, UB, уязвимость |
| **Use-after-free** | Читает/пишет после `free` | Читает мусор, портит чужие данные | Непредсказуемое поведение |
| **Утечка** | Забыла `free` | Блок занят навсегда | Память кончается, краш |

---

## Общая схема

```
malloc → [ блок занят ]
   ↓
использование
   ↓
free → [ блок свободен ]
   ↓
   ├── free второй раз   → двойной free (ОШИБКА)
   ├── обращение к блоку → use-after-free (ОШИБКА)
   └── забыли free       → утечка (ОШИБКА)
```

---

## Как писать безопасно

**Пять правил:**

1. **Каждый `malloc` → один `free`.**
2. **После `free` → `p = NULL`.**
3. **Не хранить копии указателей** без необходимости.
4. **Проверять `NULL`** после `malloc`/`calloc`/`realloc`.
5. **Использовать `valgrind` / ASan** при отладке.

**Шаблон:**

```c
int *p = malloc(n * sizeof(int));   // 1. Выделить
if (p == NULL) { ... }              // 2. Проверить

// 3. Использовать

free(p);                            // 4. Освободить
p = NULL;                           // 5. Обнулить
```

---

## Как найти любую из ошибок

**Быстрый способ — AddressSanitizer:**

```bash
gcc -fsanitize=address -g -o app main.c
./app
```

Найдёт **все три** ошибки: двойной `free`, use-after-free, утечки.

**Классический способ — Valgrind:**

```bash
gcc -g -o app main.c
valgrind --leak-check=full ./app
```

Подробнее показывает утечки, медленнее работает.

## Итог

| Ошибка | Как избежать | Как найти |
|--------|-------------|-----------|
| **Двойной `free`** | `free(p); p = NULL;` | ASan, Valgrind |
| **Use-after-free** | `free(p); p = NULL;` — не обращаться | ASan, Valgrind |
| **Утечка** | Не забывать `free`, проверять парность | Valgrind (`--leak-check=full`) |

**Одна привычка лечит почти всё:** после `free` **сразу** пишите `p = NULL`. Тогда:
- Двойной `free` станет безобидным (`free(NULL)`).
- Use-after-free превратится в **понятный краш** сразу, а не в «тихий мусор».
- Ошибку будет легко найти.
